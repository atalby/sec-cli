## Run 41 -- issue #160: docs/MULTI_TENANCY.md's auto_rotate contract

The resume point's standing move (the #129-#160 class: the next current-state
claim no sentinel section reads) landed on `docs/MULTI_TENANCY.md:59-62`, which
stated a two-branch `auto_rotate` contract:

> For each tenant section in `~/.sec/sec.conf`:
> - `auto_rotate = true`: ... `sec` attempts background key refresh using stored
>   macOS Keychain or Linux Secret Service entries.
> - `auto_rotate = false`: ... `sec` prompts interactively for manual
>   authentication (`bw unlock`, `op signin`, `vault login`).

Both branches are wrong against the live code. `bin/sec`'s `ensure_tenant_auth`
(lines 81-152) reads the key once at line 87
(`get_cfg_val "$tenant" "auto_rotate" "true"`) and references it at exactly two
places, lines 103 and 113 -- **both inside the `bitwarden|bw)` arm**:

| tenant | arm in `ensure_tenant_auth` | consults `auto_rotate` | prompt mechanism |
|---|---|---|---|
| `bitwarden`/`bw` | yes | yes | `bw-session-keeper rotate`, then `unlock` if still locked |
| `1pass`/`op` | yes | no | `eval $(op signin)`, unconditional |
| `vault` | yes | no | `vault login`, unconditional |
| `bws` | no | -- | none |
| `infisical` | no | -- | none |
| `keychain` | no | -- | none |

Two distinct drifts follow:

1. **Stale.** The `auto_rotate = true` branch is documented for "each tenant
   section" but holds for 1 of 6 backends. `op` and `vault` prompt regardless of
   the key, so there is no background refresh for them at all; `bws`, `infisical`
   and `keychain` have no auth arm, so the key is inert for them.
2. **Inverted.** The `auto_rotate = false` branch is documented as *selecting*
   the prompt, but the prompt is not gated on the key. With `auto_rotate = true`,
   if `bw-session-keeper rotate` fails to unlock, `bin/sec:120-134` still falls
   through to `bw-session-keeper unlock`. The prompt is the fallback for both
   values.

**Unguarded.** No sentinel section read MULTI_TENANCY.md lines 57-62; the existing
sections covered only the alias count/list (line 38) and the `sec.conf` mode prose
(line 9, issue #146). Same class as #129-#159.

**Fix.** `docs/MULTI_TENANCY.md:57-75` became a per-backend table (backend |
`auto_rotate` consulted | response when locked) plus an explicit sentence that the
prompt is a fallback rather than an `auto_rotate = false` branch. Sentinel section
38 derives three live sets from `bin/sec` -- the canonical backend set (the
`cli=` mapping case, plus any alias in the dispatcher's tenant regex that is not a
grouped alias, which is how `keychain` is picked up), the arms that reference
`$auto_rotate`, and the arms carrying a prompt token (`unlock|op signin|vault
login`) -- and requires the doc's table to equal them row for row, plus the
fallback anchor to survive. New mismatch tag: `auto_rotate claim`.

Test case [62] in tests/test_sentinel.sh, three probes + control, each proven
red before the guard existed:

- A: the doc's `1pass` row flipped to `yes` -> coverage names `1pass` and the
  live `'no'`
- B: an `$auto_rotate` consult injected into the `1pass|op)` arm -> coverage
  names the live widening to `'yes'`
- C: the fallback sentence re-worded -> coverage names the lost anchor
- control: an untouched seed copy exits 0 and its OK line names the check

Sentinel 61 -> 62 cases / 760 -> 776 assertions. The count-word table gained
`"sixty-two": 62`. Mirrors bumped at `profile.md:22`, `profile.md:641`

`Sentinel =` lines; HISTORY.md compacted (the 2026-10-14 #144-#159 clauses

## Run 42 -- issue #161: guard docs/SECURITY.md's plaintext-fallback contract

Third pass of the unguarded-current-state-claim sweep. Mapped which docs
sentinel.sh already guards by grepping every `docs/...` reference in it; the
master-password row (`docs/SECURITY.md:16`) and the Disk Storage Leak row's
on-disk-exception census (`:11`) had none.

This one is a **guard gap, not a doc error** -- every claim is currently true
against live code:

| Doc claim | Live code |
|---|---|
| opt-in env var gates the plaintext fallback | `bin/bw-session-keeper:72-75` store refuses unless `SEC_ALLOW_PLAINTEXT_MASTER_PASS:-0` != 1 |
| the fallback file path | `:7,9` `CACHE_DIR="$HOME/.cache/bitwarden"`, `MASTER_PASS_FILE="$CACHE_DIR/master_pass"` |
| mode 0600 | `:77` `chmod 600 "$MASTER_PASS_FILE"` |
| "refuses to store or read" | `:53-58` read proceeds only if the var `== 1`, else `[ERROR] Refusing to read` |
| infisical staging file, documented mode, unlinked | `bin/sec-migrator:227-236` mktemp + chmod 600 + `rm -f` in BOTH the success (231) and failure (234) branch |

Highest blast radius in the sweep class: a silent regression here writes a
Bitwarden master password to disk in cleartext.

Unguarded because section 25's `_SECURITY_PERMS` map binds only six paths and
`master_pass` is in neither the doc's File Permissions Architecture table nor
that map, while section 28's env-var check is one-directional (doc -> live
existence) and so never ties the opt-in var to these specific claims.
`profile.md:346-349` documented the audit *expectation* but nothing in code
enforced it.

**Fix.** `docs/SECURITY.md:57-75`-style per-claim phrasing on the master-password
row and the census clause, then sentinel **section 39**: a new `_fn_body(text,
name)` helper extracts `get_master_password` and `save_master_password` bodies
out of `bin/bw-session-keeper`; the guard derives the opt-in var (union of
`SEC_[A-Z_]*MASTER[A-Z_]*` across both bodies, must be exactly one), the store
gate (`!=` in save) and read gate (`==` in get), that the write and read actually
touch `$MASTER_PASS_FILE`, the path (reusing section 25's `_security_expand`),
and the mode from `chmod (\d+) "$MASTER_PASS_FILE"`. For the census clause it
requires the leading mode, the words session / master-pass / infisical /
staging, the inline `created <mode>` for the staging file, and the
`unlinked immediately after \`secrets set\`` anchor; then it re-derives the
infisical arm out of `bin/sec-migrator` and requires a mktemp, a chmod to the
same mode, and `rm -f` of the staging var at least twice (both branches). New
mismatch tag: `plaintext-fallback contract`.

**Three self-inflicted false positives, all fixed before trusting the guard** --
a guard must be green on the untouched tree:

1. The gate regexes were written `:-[0-9]+"\}`, but in `${VAR:-0}"` the `}`
   precedes the `"`. Fixed to `:-[0-9]+\}}"?`.
2. The infisical arm's `;;` terminator is indented 16 spaces, not 12.
3. Probe C exposed a **design hole**: only the leading `all mode 0600` clause was
   checked, so flipping the inline `created 0644` passed for the wrong reason.
   Added the `created <mode>` and unlink-anchor assertions.

**Probe-masking trap.** The first full run showed all three probes "passing" and
the control failing -- but every failure was the count-mirror drift (62 vs 63),
not section 39. Mirrors had to be bumped before the probes meant anything, and
after bumping, probe C's expected-message grep was stale and had to be corrected
to the `created 0600` message.

Test case [63], three probes + control, each proven red first: A flips the doc's
`mode-0600` to `mode-0644`; B deletes the four-line store-refusal block from
`save_master_password`; C rewrites the infisical entry to "created 0644 and
unlinked at exit"; control is an untouched seed copy.

Sentinel 62 -> 63 cases / 776 -> 792 assertions. Count-word table gained
