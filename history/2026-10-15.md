## Run 43 -- issue #162: `sec set` failures now name the stage that failed

Rather than park the issue I had just filed, I chased it. The one-off test
failure turned out to be unrecoverable *by construction*: `bin/sec` discards
every storer's stderr, so a nonzero exit leaves no trace. Underneath that was a
real defect, and it was wider than the `op` path the flake had exposed.

**The defect.** `sec set` has seven distinct ways to fail, and all seven
collapsed into one undifferentiated line at the bottom of the `case`:

```
[ERROR] failed to store secret '$key' in tenant '$TARGET_TENANT'.
```

It named the *tenant* but never the *step*. Concretely, a locked vault
(`bw create item` refused), a `bw encode` that produced nothing, an empty
`bws project list`, and a transient `op item create` failure were
indistinguishable to the operator. That is the write-honesty defect this repo
exists to prevent, and it is why #162 was worth keeping rather than closing as
"could not reproduce".

**The fix.** `bin/sec:657` initialises `set_stage`; each fall-through point
assigns it; `bin/sec:760` appends it to the existing tagged line:

| Stage | Assigned at |
|---|---|
| `payload build (existing item '<id>') produced no output` | `bin/sec:703` |
| `bw edit item '<id>'` | `bin/sec:708` |
| `bw get item '<id>' returned no data` | `bin/sec:711` |
| `bw create item` | `bin/sec:729` |
| `payload build (bw get template item \| jq \| bw encode) produced no output` | `bin/sec:732` |
| `op item create` | `bin/sec:741` |
| `bws secret create` | `bin/sec:751` |
| `bws project list returned no project id` | `bin/sec:754` |

The `if`/`else` restructure is what makes each assignment reachable; the
original `fi`-only shape had nowhere to put it.

**Diff review caught a flaw in my own fix.** The update path's condition was
`[[ -n "$encoded" ]] && printf ... | bw edit item ...`, so a *short-circuited*
empty payload and a genuine `bw edit` refusal both landed in the same `else` --
and the short-circuit case is reported as `bw edit item '<id>'`, which is exactly
the misdiagnosis this whole change exists to remove. Split into `[[ -z "$encoded" ]]`
/ `elif pipeline` / `else` so each cause is named by the thing that actually
failed. Found by reading the diff, not by a test -- the tests could not have
caught it, because the update-path stage is unreachable as a *final* report.

**Last stage wins, and that is correct.** The update path always falls through to
the create path, so an update-path `set_stage` is overwritten before the message
prints. The observable report for an empty `bw encode` is therefore the
create-path payload-build stage, which is exactly right: it names where the write
finally died. The intermediate assignments still matter -- without the split they
would leave a wrong value in place for any path that does not reach the create
stage.

**Why stage names and not the child's stderr.** The obvious richer fix is to
surface the failing command's own error text, and it would be a security
regression. `bws secret create "$key" "$value" "$proj_id"` passes the value in
argv, and a CLI echoing its arguments into an error message would print the
secret. So stderr stays discarded and the stage is named literally. No test
assertion anywhere depends on the old exact string, so the append is backward
compatible, and the `[ TAG ]` convention is preserved -- one `[ERROR]` line,
never reworded.

**Tests.** `tests/test_dispatch.sh` case **[11d]**, fifteen assertions over five
failure paths, plus three default-off stub knobs (`SEC_TEST_OP_ITEM_CREATE_RC`,
`SEC_TEST_BWS_NOPROJ`, `SEC_TEST_BW_ENCODE_EMPTY`; all `:-0`, so no existing test
is affected). Every path asserts three things: nonzero exit, the right stage
named, and -- the invariant that matters most -- **the secret value absent from
the message**.

Red-first was proven by stashing *only* `bin/sec` and rerunning:

```

  ok: bw create failure exits nonzero
  FAIL: bw failure does not name its stage: [ERROR] failed to store secret 'NEW_BW_KEY' in tenant 'bitwarden'.
  ok: op item create failure exits nonzero
  FAIL: op failure does not name its stage: [ERROR] failed to store secret 'NEW_OP_KEY' in tenant 'op'.
  ok: bws no-project failure exits nonzero
  FAIL: bws no-project failure does not name its stage: [ERROR] failed to store secret 'NEW_BWS_KEY' in tenant 'bws'.
  ok: bws secret create failure exits nonzero

```

274 ok / 5 FAIL, and the old opaque message is visible in the failure text --

**Count mirrors.** Dispatch 92 -> 93 sections, at `ADAPTERS.md:55`,
`ADAPTERS.md:264`, `profile.md:22`, and RESUME.md's mirrors-in-sync line.
`sentinel.sh coverage` caught all four on its own before I looked for them.

**Also filed: #163.** Checking the PowerShell sibling for parity turned up a

`if ($projId)` guard, so bws-installed-but-no-projects (or a failing

## Run 44 -- issue #163: `sec.ps1 set` refused to fall through to a second store

Picked #163 up rather than re-entering the doc-claim sweep, because it was a
live write-path defect on a credential surface, which outranks another doc guard.

### Grounding first: what the ps1 `set` arm actually does

`bin/sec.ps1` has no tenant dispatch at all -- unlike `bin/sec`, which has a
`case "$TARGET_TENANT" in` with a terminal `*)` arm naming the supported
backends. The ps1 `set` instead *probes the PATH* in order: `bws` (line 127),
then `bw` (line 141), then falls out to `(no backend succeeded)` (line 157).
That probe design is the source of the defect, and it also explains why the bug
is invisible in bash: bash's `bws)` arm can never fall through to `bw`, because
the backend is already chosen by tenant.

I also checked the sibling `get` arm (lines 94-106) for the same shape and
found nothing: its `bws -> bw -> op -> not found` chain is read-only and ends in
an accurate message. **Fall-through is safe for reads and unsafe for writes** --
the write path is the only one where falling through causes a side effect in a
different store. That distinction is what made the fix's shape obvious.

### The defect

`bin/sec.ps1:128-141` had no `else` on `if ($projId)`. So when `bws` is
installed but has no projects (or `bws project list` fails), `$projId` is
falsy, the `if` body is skipped, and control falls straight through into the
`bw` block -- writing the secret to the **Bitwarden Vault** when the caller
believed they were using Secrets Manager.

I had filed #163 as "falls through to try bw, else reports `(no backend
succeeded)`". The red run proved that was *understated*:

```
FAIL: sec.ps1 set silently succeeded via bw despite an unusable bws (rc=0)
FAIL: sec.ps1 fell through to bw and wrote the secret to the vault: get template item
```

Three things worse than filed, all observed rather than assumed:

1. **The secret really was written to the vault.** The `bw` stub's log line
   `get template item` is the proof -- the fall-through path executed for real,
   not merely in principle.
2. **It exited 0.** A failed write reported as success. For a secret manager
   that is the worst available outcome: any automation keying on exit status
   would record the secret as stored when it was not.
3. **It printed raw untagged PowerShell errors** (`InvalidOperation:
   Cannot index into a null array` at line 128), violating this repo's `[ TAG ]`
   CLI convention -- prose on the parse surface instead of a tagged line.

### The fix

A four-line `else` making the bws arm terminal, naming the same stage `bin/sec`
uses:

```powershell
else {
    Write-Error "[ERROR] failed to store secret '$Key' in Bitwarden Secrets Manager (bws project list returned no project id)."
    exit 1
}
```

Terminal rather than fall-through is the deliberate choice: the operator
selected Secrets Manager, and silently substituting a different trust boundary,
sync path, and blast radius is precisely the class of defect this repo exists
to prevent. `bin/sec` already treats the same condition as terminal
(`set_stage="bws project list returned no project id"`), so this is parity, not
invention. Parity is also enforced mechanically by a test that extracts the
stage string from `bin/sec` and requires `bin/sec.ps1` to carry the same one, so
neither surface can drift alone.

## Run 45 -- issue #164: dead ERR guard on the bitwarden attachment-read path

### Finding

The #129-#163 sweep had been finding *unguarded* claims; this pass found an
actual **live defect** instead, in the same failure-diagnosis family as #162.

`bin/sec:535-536`:

```bash
item_id="$(bw_list_items --search "$real_item_name" "${SCOPE_ARGS[@]+${SCOPE_ARGS[@]}}" | jq -r --arg n "$real_item_name" '[.[] | select(.name == $n)][0].id // empty')"

```

`bw_list_items` (`bin/sec:155-168`) signals failure by printing the literal
sentinel `ERR` to **stdout** (`bin/sec:163`) and returning 0. It has exactly four
consumers, and three of them capture-then-guard:

| line | site | shape | guard fires? |
|---|---|---|---|
| 498 | exact-name search | capture, then `[[ "$items_json" == "ERR" ]] && exit 1` | yes |
| 521 | all-items fallback | capture, then same | yes |
| 543 | `<item>/<field>` search | capture, then same | yes |
| **536** | **attachment item lookup** | **`bw_list_items \| jq`, then test** | **NO** |

Line 535 pipes the sentinel straight into `jq`. `jq` rejects the bare word `ERR`
as invalid JSON, writes nothing to stdout, and exits nonzero. So `item_id` is the
**empty string**, never `ERR`, and the guard at 536 is **dead code**. The script
then dies from `set -euo pipefail` (`bin/sec:4`) on the failing pipeline,
inheriting **jq's** exit status.

`printf 'ERR'` (`bin/sec:163`) is the only sentinel producer and
`bw_list_items | jq` (line 535) is the only piped consumer, so the anti-pattern
is isolated rather than systemic.

### Empirical reproduction

The naive repro -- `SEC_TEST_BW_LIST_RC=1` -- does **not** show the bug, because
line 497's search runs first and its guard at 498 exits 1 before 535 is ever
reached. The defect needs the *first* list call to succeed and the *second*
(the resolved item-name lookup) to fail, which is the realistic transient. A new
knob, `SEC_TEST_BW_FAIL_SEARCH=<q>`, fails only the call whose `--search` equals
`<q>`:

```
$ sec get MY_API_KEY/attachment/secret.txt
[ERROR] bitwarden 'bw list items' failed (exit 1): Error: vault is locked.
parse error: Invalid numeric literal at EOF at line 1, column 3
rc=4
```

Three defects in one output:

1. **`parse error: Invalid numeric literal at EOF at line 1, column 3`** -- raw
   untagged `jq` stderr reaching the user, violating AGENTS.md §8 ("the producer
   MUST emit one `[ TAG ]` line per event ... prose is never a parse target").
   The `3` is the length of the string `ERR`.
2. **`rc=4`** -- `bin/sec` contains **no** `exit 4` anywhere; its codes are
   0/1/2. Confirmed directly: `printf 'ERR' | jq -r '...'` exits 4.
3. **The guard is dead** -- confirmed in isolation:
   `captured=[]` / `GUARD DEAD (item_id is empty)`.

**Same root failure, two exit codes.** The identical backend failure
(`bw list items` exiting 1):

| invocation | caught at | rc |
|---|---|---|
| `sec get MY_API_KEY` | 498 | **1** |
| `sec get MY_API_KEY/attachment/secret.txt` | (none; dies on the pipeline) | **4** |

### The fix

Match the three working siblings -- capture the sentinel before parsing, then
guard:

```bash
items_json="$(bw_list_items --search "$real_item_name" "${SCOPE_ARGS[@]+${SCOPE_ARGS[@]}}")"
[[ "$items_json" == "ERR" ]] && exit 1
item_id="$(echo "$items_json" | jq -r --arg n "$real_item_name" '[.[] | select(.name == $n)][0].id // empty')"
```

Three lines replacing two. Makes the guard live (exit 1, as originally intended),
removes the untagged `jq` leak, and aligns the exit code with the rest of the
`get` path. No behavior change on the happy path. `items_json` is the name the
siblings already use and is reassigned again at 542.
