# Architecture Specification — `sec-cli`

**HIAE Protocol Version**: v5.39.1

## 1. Overview
`sec-cli` is a high-leverage CLI control plane that unifies secret management across Bitwarden (`bw`), Bitwarden Secrets Manager (`bws`), 1Password (`op`), Infisical, and HashiCorp Vault; `sec sync` pushes shell-exported keys to GCP Secret Manager and GitLab group variables. Runtime dependencies beyond coreutils: `jq` (housekeep) and `python3` (sync/classify).

## 2. Core Components & CLI Executables
- `bin/sec`: Main dispatcher script (get, set, run, sync, housekeep, migrate, unlock, rotate, setup-keychain, completion + aliases create/organize/keep/help/version). `set` writes are honest (issue #7): only bitwarden/bw, 1pass/op, and bws can be stored — any other tenant, or a failed store, exits 1 with an error naming the tenant instead of a silent success. `get` distinguishes a provider failure from a real miss (issue #24): `bw list items` failures surface the provider's own error and exit 1 rather than being reported as "not found". `sync` errors when the controller binary is absent (issue #23) instead of falling through to exit 0. The 1pass/op session guard tests session validity, not account configuration (issue #26): `ensure_tenant_auth` runs `op whoami`, prompts `op signin` when the session is invalid, verifies again afterwards, and aborts with a tagged `[ERROR]` instead of letting a dead session misreport "Secret not found". `get` scoping and ambiguity are honest (issue #27): `--scope <name>` restricts a `bw` lookup to a folder (unresolvable name: tagged `[ERROR] ... scope folder not found`, exit 1; the folder name `null` is rejected as reserved) and substitutes the vault in `op` synthesized URIs (other tenants: tagged refusal, exit 2); a `bw` item name matching ≥2 items without a slash form refuses with a tagged `[ERROR] ambiguous item name` listing the matches instead of silently taking the first.
- `bin/bw-session-keeper`: One-shot session helper (status/env/unlock/rotate/keep/setup); sessions stored in a 0600 plaintext file, no daemon. Master-password storage refuses the plaintext file fallback unless `SEC_ALLOW_PLAINTEXT_MASTER_PASS=1` (issue #10). Unlock passes the master password to `bw` via `--passwordenv` env, never as an argv argument (issue #16). Non-TTY unlock/setup with no stored password now exits 1 with a tagged error (issue #22) instead of dying silently on `read` EOF.
- `bin/hyer-mcp.sh`: Launcher for the host-local `hyer` MCP stdio server (issue #20): resolves `HYER_HOME` (default `~/sandbox/hyer`), tags `[ERROR]` and exits 1 when the server script, `node`, or `sec` is missing or the vault read fails, fetches `hyer-gitlab-pat` into `GITLAB_TOKEN` (environment only, never argv), then execs node directly on the resolved path — no `sh -c` string. MCP client config is the gitignored host-local `.mcp.json`; the tracked template is `.mcp.json.example`.
- `bin/sec-classify.py`: Intelligent secret classifier categorizing environment variables. Scoring reads the login fields as well as the name/notes/uris/fields (issue #25): an AWS key stored in `login.password` now classifies `cloud/aws` instead of falling back to `general`, and a GCP service-account URI (`iam.gserviceaccount.com`) claims `cloud/gcp` instead of being won by the `iam` token.
- `bin/sec-migrator`: Automated migration engine moving secrets between backends. Apply is transactional and honest (issue #7): the transaction log is flushed after every created item (and on INT/TERM), an unresolved prior transaction refuses to be clobbered (exit 1, undo hinted), and an item that cannot be written aborts with exit 1 instead of counting as migrated. Undo distinguishes absence from corruption (issue #15): a transaction log that exists but cannot be parsed tags an `[ERROR]` and exits 1 keeping the file for diagnosis, rather than being read as "zero created items" and exiting 0.
- `bin/sec-organizer`: Housekeeping engine (`sec housekeep plan`/`apply`/`revert`) — classify, move, disambiguating-rename, snapshot. Files it creates are protected at rest (issue #17): `umask 077` for every file the script writes and `chmod 700` on `~/.cache/bitwarden` on entry, so the plan lands 0600 and the cache dir matches SECURITY.md's 0700 contract instead of inheriting the caller's umask. Apply/revert refuse backends they cannot drive (issue #7): only bw and op are implemented; an unsupported backend keeps the plan/snapshot and exits 1, 1Password edits use the correct `--tags` flag and failures abort (keeping the plan/snapshot) instead of printing success. Revert is failure-honest (issue #14): an unreadable or unrestorable item tags an `[ERROR]` naming that item, sets a nonzero exit, and keeps the snapshot for retry — the snapshot is deleted and `[ OK ]` printed only when every restore succeeded.
- `bin/sec-sync-controller.py`: Central Secret Sync Controller (`sec sync`) — pushes values exported in the calling shell (`SYNC_KEYS` read from the environment; the vault is not read) to GCP Secret Manager and GitLab group CI/CD variables. Guarded against accidental prod pushes (issue #3): `--dry-run` previews key names and target endpoints with zero backend calls; a real push requires an interactive `y/N` on a TTY or an explicit `--yes` (non-interactive without it: exit 2, nothing written); zero keys present: exit 1; unknown flags: exit 2 before any work; secret values are never printed. Writes report success only when the backend accepted them — failure notices carry the backend's own stderr, every backend call has a timeout (default 60s, `SEC_SYNC_TIMEOUT` overrides), and any failed write exits 3 (contract: 0 success / 1 no keys / 2 confirmation / 3 backend write failure). All six producers (`bin/sec`, `sec-organizer`, `sec-migrator`, `bw-session-keeper`, `sec-sync-controller.py`, `hyer-mcp.sh`) emit one `[ TAG ]`-prefixed line per user-facing event (`[ OK ]` / `[INFO]` / `[WARN]` / `[ERROR]`, human detail after the tag — issue #12); usage/help screens, secret values, and plan data rows are untagged payload.
- `bin/sec.ps1`: Native Windows PowerShell wrapper for the same subcommand surface. Argument scope is honest (issue #18): a `ValueFromRemainingArguments` capture reconstructs everything past the subcommand (the `param` block otherwise swallows positionals 2–3 and leaves `$args` empty), and `run` executes tokens via the `&` call operator instead of `Invoke-Expression ($args -join " ")`, so quoted/`$`-containing tokens pass through unre-parsed. `get` mirrors the bash surface (issue #27): `--scope <name>` selects the `op` vault in synthesized URIs, and an ambiguous `bw` item name is a tagged refusal instead of a yellow notice plus first-match. A failed `op read` falls through to the tagged not-found error with exit 1 instead of a bare `exit 0` (issue #29).
- `completions/_sec`: shell completion for `sec`.
- `install.sh`: one-liner installer (bootstrap clone into `~/.sec-cli`, copy of `bin/*` to `~/.local/bin`, `sec.conf` created mode 600). Piped mode (`curl ... | bash`) never trusts a same-directory `bin/sec` — an empty script dir always falls through to the bootstrap clone (issue #19); the installer also copies `LICENSE` beside the binaries as `sec-cli-LICENSE`, warns per missing runtime dependency (`jq`, `python3`), and diagnoses a missing `git` before attempting the bootstrap clone.
- `tests/`: five zero-dependency bash suites (`test_install.sh`, `test_sync_guard.sh`, `test_write_honesty.sh`, `test_sentinel.sh`, `test_dispatch.sh`) — run manually and by CI (`.github/workflows/test.yml`, push/PR to main, actions pinned by full commit SHA); the pre-commit Step 5 does not recognize `tests/*.sh` (issue #2).

## 3. Zero-Plaintext Security Architecture
- **In-Memory Injection**: For `bws`/`op`/`infisical`, secrets reach child process environments through the vendor run-wrappers without touching disk; `bitwarden`'s `sec run` is a plain exec with no injection (audit F001, docs corrected 2026-10-09).
- **Zero-Storage Principle**: Plaintext secrets are never stored in temporary files or shell histories.
